# Unit Testing Transformation Logic (dbt 1.8+)

Generic and singular tests check **real data** against expectations. **Unit tests** check **transformation logic** against fixed, mocked inputs — you supply the rows in and the rows you expect out, so a unit test catches a wrong CASE, a bad join condition, or an edge case (nulls, boundaries) without waiting for that data to appear in the warehouse.

## When to unit-test

Reach for a unit test when the logic is complex enough to get wrong and expensive to catch in production:

- Non-trivial `CASE`/business rules (tiering, bucketing, status derivation)
- Date/window logic, slowly-changing-dimension handling, deduplication
- A macro that several models depend on
- Edge cases you can't easily produce in real data (nulls, empty groups, boundary values)

Don't unit-test a straight `stg_` rename, or a model whose grain test already covers the risk.

## Shape of a unit test

Mock every input the model `ref`s/`source`s, give an expected output, and dbt runs the model's SQL against the mocks:

```yaml
# models/_unit_tests.yml
unit_tests:
  - name: order_status_is_derived_correctly
    model: fct_orders
    given:
      - input: ref('stg_orders')
        rows:
          - {order_id: 1, paid_at: '2026-01-01', shipped_at: null}
          - {order_id: 2, paid_at: '2026-01-01', shipped_at: '2026-01-03'}
          - {order_id: 3, paid_at: null,         shipped_at: null}
      - input: ref('dim_customers')
        rows:
          - {customer_id: 10}
    expect:
      rows:
        - {order_id: 1, status: 'paid'}
        - {order_id: 2, status: 'shipped'}
        - {order_id: 3, status: 'pending'}
```

Run with `dbt test --select fct_orders` (unit tests run alongside data tests) or `dbt build`.

## Principles

- **Mock only what the model reads.** Each `given` input maps to one `ref`/`source`. Provide just the columns the logic touches — dbt fills the rest.
- **Expected values are independent.** Write the `expect` rows by hand from the rule, not by running the model. A unit test whose expectations were generated by the model is tautological, exactly as in [tests.md](tests.md).
- **One rule per test.** Name it after the behaviour (`order_status_is_derived_correctly`), and cover the edge cases (the null row above) as extra `given`/`expect` rows or a second test.
- **Keep fixtures tiny.** Three or four rows that exercise the branches beat a hundred realistic ones.
